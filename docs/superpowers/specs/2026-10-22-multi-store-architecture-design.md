## 1. 目的、范围与关键判断

建立以农业本体为统一语义入口的多存储平台，让农田、水塘、果园、作物和各类设备共同使用一套身份、语义和治理机制。每类数据进入适合它的存储，保持明确的来源、版本和关联关系。

本设计将“一主多副”解释为 **一个语义主库加多个专业数据存储**。这些专业库不是本体库的只读副本，也不能替代备份。数据库复制、高可用和异地备份是另一个部署维度。

本次范围包含可运行的数据库定义、后端读写与统一关联、旧数据迁移工具、合成样本端到端验证、部署及恢复说明，以及实施结果和资料问题清单的 Word。继续保持 `database/`、`backend/`、`frontend/` 清楚分离。本次不恢复已暂停的前端视觉重做，不把场景管理界面重新做成未经确认的工作台。必要的既有 API 兼容与生成契约更新属于改造范围。

关键判断：

1. 本体库保存类、属性、语义关系、已发布实例语义和可解释推理；专业库保存空间、高频观测和大文件等领域数据。不能用普通 SQL 表冒充 RDF/OWL 本体库。
2. 视频和图像的文件字节进入对象存储；采集时间、设备、事件、录像分段索引和数值观测进入时序库。查询某设备某时段的视频需要联查时序索引和对象存储。
3. 跨库关联使用平台 UUID、稳定 IRI、来源映射、后端 API 和可重放事件。大模型不负责唯一身份生成、数据库事务或自动裁决。
4. 首轮完成静态真实文件的接入能力、合成样本以及持续增量事件的回放验证。真实摄像头／无人机的动态采集按实装型号、协议和样本逐项接入；没有设备证据不能报告现场连通。
5. GIS 软件、底图、实测地块和真实三维成果分别管理。代码仓库中的三维功能不等于已经取得梁子湖真实三维数据。

## 3. 总体结构与各库职责

建议形成六个逻辑存储域。首版 SQL、GIS、时序、资料库可共用同一个 PostgreSQL 17 服务进程，但必须为**四个独立数据库、独立应用账号、独立迁移入口和独立连接配置**；不是在一个库里换几个表前缀。GIS 数据库启用 PostGIS。以后可以单独迁到不同服务器，业务与本体标识保持不变。

| 存储域 | 建议实现／逻辑名称 | 持有的内容 | 与本体关联 |
| --- | --- | --- | --- |
| 本体主库 | Jena Fuseki/TDB2；延续当前 dataset | 发布的类、属性、关系、实例语义、SHACL、候选／采纳／推导命名图、推理依据引用 | 稳定 IRI、发布版本、证据及专业记录引用 |
| SQL 治理库 | PostgreSQL；延续 `lzo` | 全局身份、来源映射、权限、审批、修订、审计、任务、outbox、跨库状态、资产访问登记 | `entity_id`、`event_id`、`revision`、执行规则版本 |
| GIS 库 | PostGIS；`lzo_gis` | 地块和水域边界、设备点位、位置历史、空间索引、测量资料、地形／三维成果目录 | `entity_id`、`geometry_version_id`、`asset_id` |
| 时序库 | PostgreSQL 时间分区；`lzo_timeseries` | 观测、遥测、设备事件、摄像头录像／抓拍索引、无人机轨迹点与任务时间关联 | `entity_id`、`observation_id`、`media_id`、`mission_id` |
| 对象存储 | S3 兼容接口；首版建议 SeaweedFS | 视频、图像、文档、原始数据包、GeoTIFF、DEM/DSM、点云、3D Tiles、离线地图包 | `artifact_version_id`、SHA-256、私有对象定位 |
| 资料库 | PostgreSQL；`lzo_catalog`，文件存对象存储 | 厂商、设备型号／固件／能力版本、协议资料、农业专业资料、参考本体版本和映射 | `model_id`、`document_id`、`term_iri`、资料版本 |

身份认证服务继续使用 Keycloak 自己的数据库；外部 PostgreSQL/MySQL 继续作为业务来源，既不混入内部治理库，也不受平台迁移脚本修改。

### 3.1 为什么时序库首版建议使用 PostgreSQL 时间分区

当前团队、部署条件与应用已经采用 PostgreSQL。独立的时间分区数据库能够提供明确的时间索引、范围查询、批量写入和保留策略，并降低额外服务运维成本。它必须真实实现按时间分区和采集查询，不能只给普通表取“时序”名称。

这是本次建议，不是用户指定的品牌。首版不宣称已提供 TimescaleDB 的自动压缩等扩展能力。后续可通过时序读写接口迁移到 TimescaleDB 或其他引擎，不改变实体 ID、本体模型和统一采集协议。若确定必须使用 TimescaleDB，则在实施前调整部署与测试计划，不能运行时静默降级成普通 PostgreSQL。

### 3.2 语义主库与事实归属

“主库”指语义定义、已发布知识和统一关联入口，不表示所有二进制数据、观测行和授权表都要复制进去。Schema、规则和语义事实的改变仍经平台审批流程提交，Fuseki 不向普通用户开放写入权限。

SQL 治理库记录已接受变更、证据摘要和发布顺序；GIS／时序／资料库是相应专业数据的受控存储与查询入口；对象存储是原件字节的保管位置。RDF 中的已发布语义由这些已授权、已校验版本形成。不能让多个数据库分别自由修改同一语义属性。

空间边界的领域权威来源可为 GIS 系统，设备身份可为设备管理系统，生产属性可为经营系统。字段权属仍由版本化规则决定，不能因为某数据先到本体库就自动获得最高权威。

### 3.3 部署与备份

初始单机模式保持 8 核、32GB、SSD 基准。四个逻辑 SQL 数据库可共享一个进程；Fuseki、对象存储、Keycloak、API 和 worker 独立服务、独立持久卷。连接配置支持 GIS、时序、资料库各自换主机。对时序批次、推理和地图转换实施可配置并发与资源预算。

单机共享进程存在共同故障域，应在文档中明确。这里的“副库”不提供灾备冗余；备份必须包含各库、RDF、对象文件和恢复所需配置。主从复制和高可用集群留作后续部署能力，不在本次虚构成已完成。

## 4. 统一本体 ID 与跨源实体对齐

延续平台签发的不可变 UUID 与 `urn:lzo:object:{UUID}`。业务名称、IP、地块编码、GPS 坐标、序列号、设备型号均不可直接取代全局身份。

来源身份使用明确的复合键：`source_namespace + source_instance + collection/table + canonical_source_key`。保存来源键原值、规范化规则版本、映射证据、有效区间和审核记录。对已确认映射重复导入应返回同一实体；同名、邻近位置、相同型号只产生候选匹配，不能自动合并。

区分这些身份：

| 身份 | 含义与约束 |
| --- | --- |
| `entity_id` | 物理设备、地块、农场等实体的全局身份；主管理归属变化不改 ID |
| `model_id` | 一种设备型号的资料身份；一百台同型号设备仍是一百个实体 |
| `channel_id` | 摄像机／录像机通道；保留父设备关系，不冒充物理设备 |
| `observation_id`／`media_id` | 一次观测／一份媒体资产；不与实体 ID 混用 |
| `event_id` | 一次平台接受的变更或批次；跨库重试保持不变 |
| `revision`／`version_id` | 记录或发布版本；追加修订，不覆盖历史身份 |
| 内容哈希 | 文件或规范化载荷的完整性与重复判断依据；相同文件不意味着相同业务事件 |

合并保留原 ID、来源映射与重定向记录，需独立审批。拆分、错配修正须保留受影响版本与证据，不能通过改字符串批量“修复”。源记录删除只撤回相应支持、标记失效；不能级联删除实体、文件、历史或其他来源事实。

跨农场共享设备保持一个主管理归属和多个服务关系。授权范围、服务范围、物理位置和主管理归属分别建模。观测绑定采集时有效的设备位置和服务对象版本，不能用当前归属改写历史。

## 5. 跨库写入、同步与查询

### 5.1 统一变更信封

统一信封至少包含：`event_id`、`entity_id`、来源身份、操作类型、载荷／原件摘要、`observed_at`、`received_at`、时钟依据、来源记录号／游标、Schema 版本、映射版本、规则／执行包版本、证据引用、`data_nature`、预期对象修订号。时间缺失和未知值保持显式，不能用接收时间伪装设备测量时间。

命令、静态导入、手动／定时增量和未来 CDC 使用同一处理管道：解析 → 身份映射 → 候选与冲突 → 语义校验 → 接受记录 → 专业库落库 → RDF 更新。不同源只实现协议读取与标准化适配。

### 5.2 事务模型

不引入跨 PostgreSQL、Fuseki、S3 的分布式原子事务假设。采用现有 outbox 加专业库 inbox／幂等写入、状态回执和一致性检查：

1. 文件先写私有暂存并核验摘要。仅字节上传成功不表示业务接受或发布成功。
2. 后端在治理库统一校验权限、对象版本、规则和证据；单个事务提交接受记录、修订／审计、outbox。高频采集按批次和清单登记，不为每个原始采样点强制生成整套 RDF 修订。
3. worker 向目标专业库写入固定版本及 inbox 处理记录，在该目标库的同一事务内完成；重复事件无副作用。同一事件 ID 内容不同必须报冲突。
4. 目标回执记录事件、摘要和版本水位。进程在目标提交后崩溃，重试可读取 inbox 回执，不重复落库。
5. 所需专业数据就绪后才允许相应 RDF 版本成为可见采纳事实。未完成状态为 `pending`／`partial`／`failed`，不能返回“全部同步成功”。
6. 失败可重试、暂停、隔离；保留原因与原始输入。对账检查缺失、错版本、摘要不符和无引用原件，并给出可审核的修复任务。

只做按事件的受控顺序与每对象版本比较，不要求所有专业库全局锁步。较旧事件不得覆盖较新专业记录；撤回、合并和规则重算使用同一机制，不再保留旁路 SQL 写法。

### 5.3 空间写入从当前事务中拆出

空间输入先由 GIS 服务接口执行几何有效性、CRS 与转换校验，生成规范化结果及转换版本摘要。治理库命令接受的是这一确定载荷；写入 GIS 时校验摘要一致。GIS 不可用时，空间编辑不能标为成功；其他不依赖 GIS 的对象操作可继续。

治理库的不可变修订可以保留回放所需空间载荷／原件引用，但面向地图的空间索引和专业空间查询仅由 GIS 库提供。原 `semantic_geometry` 先作为迁移来源和受控兼容读入口；切换后不再作为第二个可独立修改的空间权威表。

### 5.4 读取与权限

前端只访问后端。跨库 join 由后端使用已授权实体 ID、版本引用和批量查询完成；不依赖跨服务器外键、数据库链接或客户端直接连库。

列表、地图、观测、媒体、资料、图谱、SPARQL 和导出均从治理库获得当前授权。专业库中的范围字段用于检索，不是永久授权证据；撤销共享后不能因旧索引仍含范围而继续读取。跨对象关系两端及证据资源分别检查权限。

结果返回所用版本、数据性质和同步状态。要求最新版本的查询若存储落后，应明确等待／返回未就绪；允许历史读取的接口必须明确标明版本。分页采用稳定的时间与 ID 游标，过滤权限后再正确计算分页，不能先截断后漏项或泄露未授权数量。

SPARQL 继续查询受权语义图。首版不将外部 SQL／S3 包装成任意可执行的 SPARQL `SERVICE`；“对象＋地图＋最近观测＋媒体＋资料”由后端聚合 API 实现，并返回各部分版本与缺失状态。高频观测仅按配置将有语义价值的事件、统计或引用纳入 RDF，避免每帧都展开成大量三元组。

## 6. 专业数据模型与接入策略

### 6.1 GIS 库

主要模型：`geometry_versions`、`geometry_heads`、`device_location_versions`、`spatial_assets`、`survey_points`、`spatial_reviews`、`inbox_events`。确切表名允许实施者按现有规范调整，但领域信息不能丢失。

每份几何记录实体 ID、几何版本、原始和规范化几何、来源 CRS、目标 CRS、转换方法／版本、采集时间、精度／质量、证据及有效区间。农场、农田、水塘、果园使用通用对象类型，不能每个场景各写一套空间表。

设备位置区分固定点位、带有效期的移动历史、无人机轨迹。经纬度和高程不混用；水平 CRS、垂直基准、安装参考点和误差分别保存。无高程不能用 0 伪造真实三维位置。

栅格、DEM/DSM、点云和 3D Tiles 文件放对象存储；GIS 保存覆盖范围、采集时间、分辨率、基准、文件清单与版本。可按 STAC 的时间／空间／资产组织方式设计目录，首版不因此承诺完整 STAC API 服务。地下／水下地形不能从一般卫星底图推断。

本次实现空间数据与现有二维地图接口的拆分兼容，以及三维成果文件包与元数据登记、完整性校验、审核状态。真实三维重建、摄影测量生产线和新的三维交互页面不在本次默认范围；已有真实成果可作为后续验证输入。三维资料质量使用“来源未核／仅展示／专业核验通过”等明确状态。

### 6.2 时序库

主要模型：按月或可配置周期分区的 `observations`、`device_events`、`media_timeline`、`track_points`；以及去重登记、版本更正、批次清单和 inbox。分区维护由受限维护角色执行，API 账号不能随意建表或删分区。

观测字段包含实体、测点／指标 IRI、原始值和单位、标准化值和单位、测量方法、设备固件／校准版本、来源记录号、采样／上报／接收时间、时间质量、空间绑定版本、证据、状态和数据性质。未知、缺测、无效和数值零严格区分。

去重键为来源命名空间及来源记录身份；没有来源号时使用明确登记的设备序列／批次规则，不能只用时间和值猜测。全局去重登记与该分区数据写入在时序库同一事务内完成，避免分区键改变导致重复。修改追加更正版本，保留原值；同键异内容隔离为冲突。

提供批量写入、按设备／指标／时间范围查询、最新有效值、分页、质量过滤和确定性基础聚合。支持晚到、乱序、时区转换和断点回放；采集新鲜度与通信在线状态分别表示。

分区与保留策略可配置，默认不物理清理来源证据和已被裁决引用的记录。本次先提供保留策略预览与受控归档接口；未确定媒体和观测保留时长前，不执行自动清理。不能以“节省空间”为由删除不可变历史。

### 6.3 对象存储与媒体

统一 BlobStore 接口覆盖本地兼容和 S3 实现；默认部署建议采用 SeaweedFS S3 服务，旧本地文件可逐批迁移。所有调用经同一工厂／依赖注入，禁止地图、导入、语义导出继续绕过配置直读旧文件夹。

文件内容按摘要校验，业务资产版本与文件内容分离；对象键不包含可猜测的业务秘密。读取先检查实体／资产当前权限。媒体通过鉴权后端支持 HTTP Range 或等效受控分段读取；不向浏览器暴露永久凭证和裸私有地址。密钥只在部署环境中提供。

现有普通附件默认上限不能直接套在大视频／三维包上。本次增加有配额和完整性校验的分段／可恢复上传会话，明确会话期限、最后提交、总大小、分片摘要和失败清理；按媒体用途配置上限，不通过把全部文件读入内存实现大文件上传。最终完成仍需要整件摘要、长度和版本登记。

媒体时间索引保存设备／通道、开始与结束时间、实际采集或抓取时间依据、编码／分辨率等已知信息、对象资产版本、录像序号、缺口和校验状态。原件、缩略图、转码件、算法结果分别登记，派生文件不能覆盖原件。

对象存储版本功能不能替代平台不可变审计。平台禁止原版本覆写；S3 服务自身的对象锁／保留能力只在实际配置并验证后列为已实现。未被正式接受的暂存对象在宽限期后可由受限维护任务清理，先核对活动上传、重试任务和正式引用。

### 6.4 资料库

主要模型：`manufacturers`、`device_models`、`model_versions`、`capability_profiles`、`protocol_profiles`、`documents`、`document_versions`、`reference_ontologies`、`term_mappings` 和 inbox。

设备型号资料包含厂家、完整型号、硬件／固件版本、设备类别、数据和控制能力、协议、编码、采样／抓拍限制、接口许可、离线可用性、资料证据、验证状态及适用范围。报价、计划采购、已安装、已联通、已验收分别记录，不能将报价设备数量当作实装数量。

专业资料保存标题、作者／机构、发布日期、适用农业场景、语言、版本、许可、来源 URL、原件哈希、关联术语／实体、审核记录及修订关系。首版支持结构化检索与资料关联；不默认增加向量数据库、自动 OCR 或大模型服务依赖。已有人工整理的摘要可以入库，但必须标明来源与整理人。

参考本体按固定版本／快照、哈希与许可导入离线包，经过映射和兼容性审核后形成发布版本。不能每次启动都从互联网自动加载最新本体。设备型号、专业文献与本体类是不同对象，资料存在不意味着其中每个结论都被平台采纳。

## 9. 旧数据迁移与回滚

迁移范围是当前 `Ontology-Farm` 的数据模型及用户指定的运行数据，不能把开发机上其他项目数据库直接作为可迁移生产库。

1. 盘点与备份：登记旧版本、水位、记录数、哈希、对象引用、授权和现有文件根目录；先验证备份可以读回。
2. 新库初始化：新增独立数据库、最小权限账号和独立迁移链，保留现有 Alembic 历史；不修改旧迁移脚本伪装升级。
3. 快照回填：按固定水位从旧空间表、资产及资料来源导出，保留 UUID、修订号、证据和原件哈希。新库导入可重复执行并保留检查点。
4. 增量追平：回填期间产生的事件经 outbox 追平；按实体／版本／摘要对账，缺失或冲突阻止切换。
5. 受控切换：独立管理员批准高风险迁移，必要时短暂停止相关写入，确保旧写入路径已隔离；切换后读取新库，返回实际水位。
6. 验证：旧新几何值、权限、历史、证据及关键查询逐项比较；迁移模拟包含失败中断后恢复。
7. 回滚：读路径可退回仍然完整且版本满足要求的旧存储。切换后若已有新写入，必须先用事件日志补齐旧兼容存储或从新备份恢复；不能只改连接串丢掉新数据。数据库破坏性降级不是默认回滚方式。

旧库及文件在确认保留方案之前不删除。迁移工具默认为预览／校验模式，明确目标并有当前备份后才能执行生产切换。此处管理员确认是平台高风险治理的一部分；本地隔离测试的建库和可逆演练不需每步向用户重复请示。

## 11. 验证与交付标准

本次完成的判断依据是实际测试与运行记录，不是目录数量或 SQL 文件数量。

| 类别 | 必须验证的行为 |
| --- | --- |
| 建库与隔离 | 四个独立逻辑 SQL 库、独立账号／迁移；GIS扩展与时间分区实际存在；错误账号拒绝访问 |
| 真实存储读写 | PostGIS、时序分区、资料库、S3、Fuseki 持久化写入并在重启后回读；不能全以 mock 代替 |
| 跨域场景 | 农田、水塘、果园各有样本；同一设备关联型号、位置、观测、图片／录像和 RDF，最终 ID 一致 |
| 幂等与冲突 | 同事件重放不重复，异内容同键报冲突，乱序不倒退，源删除保留身份与历史 |
| 故障恢复 | 专业库停机、S3上传中断、目标已提交但回执丢失、重复 worker 与重启恢复；未就绪不报全部成功 |
| 权限 | 跨区域读取与关系遍历、媒体 Range、资料原件、历史及导出均受后端授权；撤权后拒绝 |
| 语义回归 | 已有 OWL／SHACL／SPARQL、推理解释／撤回、版本审批和来源追溯无回归 |
| 迁移 | 从隔离旧库回填、增量追平、对账、切换、失败重试与含新写入的回退演练 |
| 离线 | 不依赖外部模型／API／字体／地图资源完成样本写入、查询、地图与关系读取 |
| 恢复 | 从协调备份清单恢复各库和文件，检查 UUID、版本水位、文件摘要、权限与本体一致性 |
| 性能 | 可复现测试报告保留 P50/P95、吞吐量、错误率、CPU与内存；记录实际硬件，不把开发机结果充当标准环境结果 |

继续沿用 10 并发用户、1万实体、10万关系作为既定整体验收基准，不作为代码上限。本次增加可配置观测量、媒体大小／数量、迁移批量和晚到比例。未取得真实设备参数前，性能报告明确使用哪些合成输入，不承诺特定摄像头数量和录像保存天数。

容量估算采用可核对的输入：视频字节约为 `通道数 × 平均码率(bit/s) × 记录秒数 ÷ 8`，另计副本、索引、缩略图与备份；观测规模由设备数、测点数、频率和保留时长计算。磁盘不能只按实体／关系条数估算。

当前环境尚无可用 Docker 引擎。实施可先在隔离的原生服务中验证后端与各库；Compose 必须在实际可用引擎／服务器上运行后才能记为通过。如果环境无法提供，报告单列“未执行及原因”，不把可运行部署文件等同于已完成容器验收。安装会重启系统或改动宿主机虚拟化的事项另行说明；不影响先完成可做的编码与原生验证。

## 13. 需要用户确认的工程建议

请整体确认本设计，或指出需要改动的部分。建议一次确认以下核心边界：

- “一个语义主库＋五类专业存储”，单机先逻辑分库并允许以后分服务器。
- 延续 UUID＋稳定 IRI，以后端规则／事件关联各库；大模型保持可选候选辅助。
- 时序先采用独立 PostgreSQL 时间分区；对象存储采用 S3 接口并建议 SeaweedFS。
- 先完成静态文件、通用增量与模拟回放；真实设备协议、真实三维测绘由资料清单约束，不能用合成数据代验。
