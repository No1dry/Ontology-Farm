## 1. 建设目的与文档约定

建设面向梁子湖农业的通用 Ontology Platform，以统一、可扩展的农业本体、稳定对象身份和受控数据治理，为农田、水塘、果园及多种农业设备提供共同基础。

首版同时覆盖三个场景，但不要求完成各场景全部行业业务。重点是让本体建模、动态实例管理、语义推理、数据接入、权限治理和前端管理机制真正可用。后续增加场景、设备类型和来源时，应复用这些核心机制。

总体原则是数据身份唯一、权限边界清晰、裁决可追溯、历史不可篡改。身份、共享授权、裁决复核、历史修订与版本对比均作为通用平台能力，不针对某个农业场景或设备类型硬编码。

本设计结合根目录《梁子湖农业+Operational+Ontology+Platform.md》与后续需求讨论。用户在讨论中的明确决定优先于原文建议。本文标注为“工程建议”的内容保留其工程决策来源，已随完整设计获得确认；具体接口、依赖版本和任务顺序由实施计划细化。其余未冲突的原文原则继续适用。

用户已确认完整设计。下一阶段先制定实施计划，再按选定执行方式初始化工程、安装依赖和编写产品代码。

## 3. 首版产品范围

### 3.1 必须可用的工作流

1. 管理员配置用户、角色、用户组和对象范围。
2. 本体编辑者在前端维护类、属性、关系、约束和字段权属，检查继承和影响。
3. 提交高风险变更，由另一名审核人审批后发布。
4. 在已发布类型下自动生成表单，创建、查询、修改和停用实例。
5. 配置 PostgreSQL、MySQL 和文件来源，完成映射、预检、实体对齐、导入及持续同步。
6. 查看候选和冲突，逐字段审查来源、原值、标准化结果与证据，采纳或拒绝。
7. 从图谱、地图和实例详情查看同一对象，执行受权限约束的语义查询。
8. 查看派生事实的解释路径，撤回依据后观察相关结论重新计算。
9. 修改治理规则，预览影响，经审核发布并分批重算历史数据。
10. 在离线内网环境完成上述核心流程，执行组合备份、恢复和负载测试。
11. 在不同区域查询同一个共享对象，分别管理其主管理归属、服务关系和显式授权，调整共享授权不复制实体。
12. 查看定义、对象、来源、裁决和推理的历史修订与差异，追踪修改前后状态、具体责任人及关联任务。

### 3.2 前端工作台

沿用原文的中文优先、独立湖域农业视觉方向，以及 React、TypeScript、Vite 技术主线，作为工程建议。原文的湖蓝、稻绿、深石墨主题和桌面工作台布局作为初始设计基础，具体外观在视觉审阅中调整，不复制旧梁子湖、Semantica 或 WorldWideView 前端。

首版包含总览、本体设计、实体管理、关系探索、地图、规则与质量、数据源、版本与治理、用户权限和系统设置。审核、冲突、重算等能力可以在这些页面内组织，不强求每一种任务单独成为一级菜单。

本体设计须支持类树、Schema 画布、属性面板、继承预览、约束编辑、草稿恢复、撤销/重做、未保存提示和乐观锁冲突提示。实例列表、动态表单、详情、关系、来源、历史随发布元数据变化。

地图和关系图共享对象选择与详情入口，支持交叉定位。来源、真实性、候选/采纳/派生状态、Schema/规则版本、同步状态须可识别。未实现的功能不以假按钮或静态成功状态展示。

桌面为主要使用方式；窄屏提供查询和轻量操作。键盘操作、焦点、状态文字和可访问的列表替代操作沿用原文要求。高级编辑器和大图不要求在手机上提供完整桌面体验。

### 3.3 后续扩展边界

首版不建设完整灌溉调度、无人机飞控、生产经营流程、畜牧管理、3D 孪生、视频平台或完整溯源门户。文档自动解析与 AI 抽取、实时 CDC、高级 OWL 推理、多维属性授权、多级审批和公网正式服务保留扩展接口。

独立的 P2 Action Engine 不因通用权限接口出现而自动加入 P0＋P1。首版发布、采纳、停用、合并、重算、回滚等治理命令均受权限和审计控制；未来业务 Action 复用授权契约。真实设备控制保持关闭。

## 4. 领域模型与动态扩展

### 4.1 农业与空间对象

首批模型包括稳定身份基础类、农场、农业分区、农田、水塘、果园、作物类别/品种、实际种植或生产周期的必要引用、设备、组织、来源、证据和断言。

工程建议：农田、水塘、果园以共同的农业空间对象能力建模，明确其几何、经营归属、有效时间和关联设备。作物种类/品种与实际种植对象分开，分类词汇优先采用 SKOS，观测和溯源分别对齐 SOSA/SSN 与 PROV-O 的适用部分。

经营归属、空间位置、物理组成、监测目标、控制目标、挂载关系分别定义，不能把来源外键或几何邻近直接当作已确认业务关系。

### 4.2 通用设备

设备类型覆盖 Sensor、Camera、WaterGate、Pump、IrrigationEquipment、AgriculturalMachine、Drone 等，并具备稳定身份、业务别名、类型、来源、空间关联和状态时间。

同一设备在全平台只有一个 UUID/IRI 和一个主管理归属，可关联多个农场、农田、水塘及其他农业空间对象。管理归属、服务范围和访问权限分别建模；按服务区域重复导入时复用已确认的设备身份，不为每个区域另建设备实体。无法确定身份的记录仍走候选对齐与审核。

位置、挂载、监测或服务关系不自动改变主管理归属，也不自动授予查看、使用或操作权限。首版支持明确的共享授权配置与调整；后续归属转移保持设备身份、来源绑定和历史链不变。首版预留转移命令、影响分析和审批接口，后续转移流程复用通用治理机制。

工程建议：类型、能力、组件/挂载关系分别建模。例如无人机挂载摄像头或传感器时，通过独立对象和挂载关系表达，避免因兼具能力而重复创建同一设备。模型允许约定范围内的多重继承，并检查循环和约束冲突。

设备协议、视频访问、遥测或执行器由适配器承担。新增类型不等于自动实现某个厂商的设备驱动。

### 4.3 可配置范围

前端须可维护类与父类、标签、描述、属性类型、单位、枚举、基数、关系方向/端点、常用 SHACL 约束、属性权属、表单元数据、来源映射、对齐规则、冲突规则及权限配置。

工程建议：首版采用结构化规则和白名单操作符，支持字段取值、类型转换、单位标准化、条件、比较、组合条件、稳定键匹配及明确优先级。不允许运行任意上传代码或直接 `eval()`。UI 元数据与 OWL/SHACL 语义定义分开。

新增同类来源、常规农业类型、字段及规则通过配置完成；全新数据协议、专有转换或业务执行器可新增插件，不能要求修改核心语义服务。

## 5. 架构与数据权威边界

采用模块化单体和独立可部署组件。逻辑模块不要求拆成大量微服务。

| 部分 | 职责与边界 |
|---|---|
| Web 工作台 | 标准登录接入，元数据驱动界面；不直连存储写端口 |
| API | 统一鉴权、Schema/对象/关系/治理命令、查询契约、错误报告 |
| Worker | 同步、图谱投影、推理、影响试算、重算、导出及恢复任务 |
| 外部 PG/MySQL | 业务数据源，首版只读接入；与内部事务库独立 |
| 内部 PostgreSQL | 身份与映射、业务修订、断言登记、草稿和发布、审核、权限、任务、审计与 outbox |
| PostGIS | 平台空间对象的权威几何、坐标来源、几何修订及空间查询 |
| Fuseki/TDB2 | 已发布本体、SHACL、采纳/候选/派生/溯源图的 RDF 持久化及 SPARQL 服务 |
| Semantica Adapter | 封装经验证的本体处理、SHACL/语义能力及未来抽取能力，独立于业务代码 |
| 身份服务 | Keycloak 首版提供 OIDC 登录与账号生命周期，业务授权留在平台 |
| 文件存储 | 附件、原始来源快照、规则试算输入、地图包和导出物，记录摘要与版本 |
| 地图资源服务 | 本地瓦片、PMTiles 范围读取、地图样式/字体/图标和可选在线来源 |

内部 PostgreSQL 延续原文事务职责；Fuseki/TDB2 替换原文默认 Oxigraph，不能把 RDF 降为事后导出格式。语义查询和推理必须真正使用 RDF/OWL 模型。

工程建议：后端延续 FastAPI、Pydantic、RDFLib、pySHACL 主线；Semantica 的实际能力纳入可验证调用链，不复用其内存中的 Explorer 草稿/版本状态。具体版本及主校验器的连接方式在实施计划中经兼容核查锁定，不能默默省略 Semantica 集成。

工程建议：文件存储初版采用独立接口和受控持久卷，实现摘要寻址、版本和权限访问；后续可更换兼容 S3 的存储服务。不要将原始大文件塞入 RDF 或 PG 大型 JSON 字段。

### 5.1 一致性

应用命令在内部 PG 事务内提交业务修订、审计和 outbox。语义适配器幂等投影到 RDF，并记录已处理修订、水位和失败状态。客户端可见 `pending / synced / failed`，不能把 PG 提交当作 RDF 已更新完成。

支持乱序检查、重复事件去重、失败重试、隔离失败任务、差异对账和从权威记录重建图谱。普通用户只能通过受控 API 写入。

Schema 发布采用可恢复状态机，完成校验、批准版本安装和可读性检查后才切换有效版本；跨 PG 与 RDF 不承诺未经设计的原子提交。

## 6. 身份、字段事实与溯源

实体使用平台生成的 UUID 和稳定 IRI；来源编号、中文名和设备序列号是可变化的别名或来源身份。外部身份键包含来源系统、来源实例、表/集合和规范主键。

跨来源对齐仅在明确业务唯一键、已确认映射或经审核的合并依据下执行。名称相似、位置相近或模型相似分数只能形成候选，不自动合并。切换来源保留已确认对象的稳定身份；合成记录不得仅因名字相同而自动认领真实对象。

| 事实层 | 保存内容 | 对业务查询的作用 |
|---|---|---|
| 原始 | 来源报告的值、类型、单位、时间、来源键和不可变快照引用 | 原始证据，不自动代表真实或采纳 |
| 候选 | 标准化值、匹配建议、冲突、证据及处理版本 | 独立审核视图，不默认参与正式推理 |
| 已采纳 | 当前有效属性和关系、有效时间、来源支持及裁决 | 默认业务事实查询 |
| 派生 | 基于有效事实和规则推导的结论及证明 | 明确标记，可解释、可重算与撤回 |

每个字段值和关系断言保留独立标识、来源支持、原始值、标准化值、数据性质、业务有效时间、系统记录时间、规则/Schema 版本及裁决记录。不同来源支持同一结论时分别保存支持关系。

工程建议：用稳定 Assertion IRI 与标准 RDF 溯源、陈述具体化（reification）表达需要携带元数据的断言；不依赖专有图存储语法。具体表结构和标准 RDF 词汇映射由工程设计细化。

`synthetic / test / imported_unverified / verified` 与 `candidate / accepted / rejected / withdrawn` 是不同维度。人工采纳不自动等于现场核实，未经核查的模拟或抽取结果不能变成 `verified`。

## 7. 统一接入、持续同步与 CDC 扩展

### 7.1 统一流程

连接器读取或文件解析 → 原始快照 → 来源字段映射/标准化 → 身份匹配 → SHACL 与业务校验 → 权属/冲突判定 → 必要人工审核 → PG 事务与审计 → RDF 投影 → 推理更新。

所有解析器输出统一的来源记录或变更批次；场景业务规则不能写在 CSV、MySQL 等具体解析器中。映射配置、字段含义、单位、空值、来源键和归属范围可预览并版本化。

### 7.2 同步契约

统一变更事件至少包含来源标识、来源记录键、操作类型、来源版本或游标、业务时间、接收时间、快照引用、内容摘要和幂等标识。

首版提供全量、手动增量、定时增量。数据库的更新时间字段、稳定键或快照差异作为可配置变更检测方式；若来源无法可靠提供增量依据，显式退回快照对账，不能声称已捕获所有变化。

删除通过明确删除标志、来源事件或一次完整且成功的快照对账识别。连接失败、部分分页失败或范围变更不能被解释为来源全量删除。

同一来源记录的不同版本有顺序和重复处理检查，任务保留检查点；重启后继续处理，重复导入不生成重复实体。相同幂等键对应不同内容应报告冲突。

未来 CDC 连接器只替换变更获取环节，输出同一变更契约，复用映射、身份、权限、冲突、审核和投影处理。

### 7.3 删除与失效

来源记录删除后，先失效对应来源绑定和它支持的字段/关系事实，保留快照和历史。存在其他有效支持时，实体和结论继续存在。

工程建议：若实体失去全部有效来源支持，标记为待核查或按明确生命周期规则停用；不自动物理删除。平台自有备注不被来源删除覆盖。合并、停用、撤回及解除绑定都保存可审计的修订。

已失效事实不继续进入默认当前事实查询；依赖它的推理结果随之重算。历史视图保留当时事实及规则，不通过删除历史达到“回滚”。

## 8. 文件与证据

| 类型 | 首版行为 |
|---|---|
| CSV、XLSX | 选择工作表/表头与字段，配置类型、单位和键，通过通用接入流程处理 |
| JSON | 配置记录路径与字段路径，进入同一来源模型 |
| GeoJSON | 解析几何及属性，记录 CRS、来源与实体映射，几何写 PostGIS |
| RDF/Turtle、JSON-LD | 标准解析、预览与导入导出；区分 Schema、Shape 与实例数据 |
| PDF、Word、图片 | 保存原件及版本、摘要、来源、审核状态，关联实体、字段或关系证据 |
| MBTiles、PMTiles | 作为地图资源登记、校验、配置和服务，不用来替代业务几何库 |

批量导入提供只读预检、按行/字段错误定位、变更统计、重复内容识别和正式应用记录。失败条目及成功条目的状态必须可核对，不能把部分成功报告为全部成功。

语义文件不绕过发布治理。Schema/Shape 导入形成草稿并运行兼容性与风险分析；实例导入接受身份、权限、SHACL 和来源治理。工程建议：发布范围限制为约定支持的语义配置，超出范围的公理保留原件并报告，不静默丢弃或伪装支持。

附件与原始快照按权限读取，不通过可猜测的公开文件路径泄露。未来文档解析器输出候选断言及文件摘要、页码/片段位置、模型版本和提取时间，经同一审核流程采纳。

## 9. 字段权属、冲突与人工裁决

GIS 来源负责约定的空间位置、边界和面积；设备系统负责约定的设备身份和状态；农业经营来源负责经营主体及生产信息。平台自有、来源拥有、派生和只读属性分别声明策略。

规则允许确定的单位换算、格式标准化和可比较时间戳更新。时间较新只有在已确认身份、字段权属及时间含义明确时才能构成更新理由。

身份不确定、多个权威来源矛盾、规则无法判定或可能影响重要业务的冲突进入人工审核。保留当前已采纳事实与候选差异；不能静默覆盖、合并或删除。

裁决支持逐字段查看各来源、原值、标准化值、时间、证据和规则依据，记录采纳/拒绝/维持当前值的意见。实体合并属于高风险操作，并保留来源绑定、旧标识和合并历史。

### 9.1 裁决有效性与重新评估

裁决绑定具体冲突、证据快照、相关字段权属及裁决规则版本，记录审核人员、意见、时间和后续裁决关联。对应证据和规则条件未发生实质变化时，已有裁决继续有效；不能仅因再次同步或不相关配置的版本号变化就令其失效。

来源数据、字段权属或裁决规则发生重要变化时，系统自动重新评估。出现新的实质性冲突必须进入人工审核，不能直接复用旧裁决，也不能由同步或历史重算静默覆盖人工决定。无新冲突的评估同样记录输入版本、判断结果及与原裁决的联系；新裁决通过追加记录替代原裁决的当前效力，原记录保留。

工程建议：实质变化判定基于裁决依赖的字段、实体身份、来源支持、有效时间和相关规则差异；判定策略可配置、版本化并受风险审核约束。无法确定是否影响裁决时进入复核。审查期间仍有有效支持的已采纳事实保留并标记待复核；依据已失效且无其他有效支持时，按失效规则撤回当前事实及相应推理，不能把过期证据继续当作有效支持。

工程建议：如需长期人工例外，复用已有的版本化权属/裁决规则，明确适用范围、审批依据和撤销历史，与来源事实分开登记；不能把一次裁决隐式变成永久字段锁定。不另设独立的永久覆盖机制作为首版验收项。

工程建议：规则判断“重要业务”的分类以平台可配置的字段/关系风险标签与变更类型为输入；修改风险配置本身也走高风险审核。

## 10. Schema、规则版本、审批与重算

### 10.1 版本与发布

Schema 包、规则集、UI 元数据、映射配置和软件版本分别管理。已发布内容不可原位覆盖，稳定 IRI 不复用为不同语义。

工程建议：每次运行绑定一个不可变的生效快照，包含 Schema 包依赖清单、SHACL、映射/对齐/权属/推理规则版本及摘要。实体修订和断言记录所用快照，以支持解释与历史重算。

发布状态包括草稿、待审核、批准、发布中、已发布、失败及弃用；发布失败可恢复，不切换到半安装版本。正式 OWL/SHACL/规则产物作为不可变发布文件归档，记录摘要和版本注册表，并形成可提交 Git 的发布清单。

工程建议：Git 作为可审查版本归档，内网应用不以访问远程 Git 为发布前提。发布任务生成确定的归档产物；版本注册表和本地不可变产物驱动恢复，Git 归档状态单独可追踪。

### 10.2 风险与职责分离

| 变更 | 最低处理要求 |
|---|---|
| 不改变语义/业务契约的标签、描述修订 | 有发布权者可直接发布，仍保留校验、版本和审计 |
| 类、属性、关系等 Schema 结构变更，包括新增 | 高风险，由不同人员审核 |
| 字段权属、重要关系规则、实体合并 | 高风险，由相应权限的不同人员审核 |
| 批量重算、回滚、风险判定策略修改 | 高风险，由相应权限的不同人员审核 |

系统综合变更类型、影响范围和预览结果判级，普通编辑者不能降低最低风险。管理员也不能以同一平台身份自审高风险提交。

批准绑定具体变更摘要、基线版本和影响报告。内容发生实质变化，或执行前出现会改变审核结论的数据变化时，重新预览和审核。执行前再次检查权限及版本，防止用旧批准覆盖新的有效数据。

审批记录包括内容、影响分析、意见、提交人与审核人、时间、所用规则版本和执行结果。首版提供单级独立审核，数据模型与策略接口预留多级审批。

### 10.3 兼容性与历史实例

发布检查继承循环、IRI 冲突、模块依赖、受影响实例、SHACL 违规、关系变化、动态表单差异和权限影响。

工程建议：兼容变更可按流程发布；会令已有有效数据失效的变更，必须明确迁移范围、历史校验版本和过渡策略，缺少处理计划则阻止生效。首版复用通用影响分析和受控重算能力，不提供任意脚本迁移。

IRI 更名采用弃用与替代映射。删除定义不能静默删除历史数据；历史按原版本解释，当前事实按明确生效策略迁移。

### 10.4 影响分析与重算

基于原始快照和确定的输入水位试算，展示受影响实体、字段、关系、冲突、推理结论及前后差异。试算不修改正式事实。

影响报告须区分仍适用的既有裁决、需要重新评估的裁决及新增待审核冲突。规则发布与受控重算均复用第 9.1 节的裁决契约，批量重算获批不等于可以绕过逐项实质冲突的人工复核。

新版本发布后，新启动的同步批次使用新版本；已运行批次固定原快照，任务状态显示版本。旧版本任务不能用过期结果覆盖新版本下更晚的修订。

历史重算仅处理经确认的范围，分批推进。状态至少覆盖待审核、已批准、排队、运行、暂停、部分失败、完成、回滚中和已回滚，记录检查点及逐项结果。

暂停停止领取新批次，已提交批次保留，进行中的事务按明确边界完成或中止。失败重试针对失败项且幂等，恢复不要求重新导入全部来源。

回滚采用可审计的补偿修订，不删除原始快照、历史或裁决。若目标记录在重算之后又发生有效更新，生成冲突供审核，不直接覆盖。规则生效版本切回和某次重算结果回滚是两个独立操作。

### 10.5 历史修订、版本对比与不可变记录

首版历史查询覆盖本体定义、实体属性、对象关系、空间几何、来源证据、规则版本、人工裁决和推理结果。支持按对象、版本、时间范围、操作者或任务追踪变更；版本对比显示增加、修改、失效和撤回，以及关键变更前后的状态、原因和具体责任人。空间修订支持几何及属性差异查看，规则与定义修订显示语义内容差异，推理历史保留当时结论与依据。

人工操作记录稳定用户身份；自动更新记录任务身份、发起人或调度配置责任人、执行版本及关联请求，不以笼统的“系统修改”代替责任追踪。历史证据引用原始快照与当时版本，不能读取当前值来冒充历史值。

已提交修订、发布产物、裁决和审计记录仅追加，不允许通过业务接口或普通平台管理员权限原位编辑、删除历史。错误通过新的更正、失效或补偿修订处理。当前查询投影可重建和更新，历史权威记录与其分离。

工程建议：在存储权限与约束层限制历史记录的更新和删除，为内容及关联关系保存摘要，使用可验证的修订链和独立备份清单检查异常变更或缺失。防篡改校验范围、运维权限隔离及恢复验证步骤在实施计划中明确，不把单个可随数据一起改写的哈希字段当作完整保障。

历史读取与版本对比按当前有效权限执行，覆盖历史关系、来源证据及推理依据；曾经可访问某区域不构成永久的历史访问权。若涉及已失效的区域或专门审计范围，需当前明确授权。历史权限检查不能通过恢复旧授权配置来绕过。

保留修订顺序、业务有效时间、系统记录时间、依赖版本和快照接口，为后续历史快照与指定时间点状态重建提供输入。首版交付上述修订查询和对比，不要求任意历史时点的全平台地图、图谱及 SPARQL 完整回放。

## 11. 语义校验与推理

### 11.1 首版语义配置

必须实现：

- 多级 `rdfs:subClassOf` 闭包及实例类型推导。
- `rdfs:subPropertyOf` 的约定继承语义。
- 显式声明的 `owl:inverseOf`。
- 显式声明的对称属性和传递属性。
- 对各规则输出可验证的解释、重算及撤回结果。

不能因名称像“包含”“监测”就自动赋予传递或对称语义。首版不承诺完整 OWL 2 DL。

### 11.2 校验与推理职责

工程建议：SHACL Core 为首期执行基线，结构化界面覆盖常用字段类型、必填、基数、范围、枚举、模式及关系端点。高级形状的支持范围明确登记，未经实现的构造不作为已支持能力展示。

OWL 推理不替代输入验证。关系端点检查使用被确认的类型及合法类层次，不能先利用待写关系的 domain/range 推出类型，再以该类型证明此关系合法。

草稿可允许不完整；激活或采纳前使用严格校验配置。错误定位到字段、Shape、实例与约束，保留机器可读报告。

### 11.3 推理结果与依据管理

仅将约定的有效、已采纳事实输入正式推理，候选事实不默认混入。派生图与基础事实分离，记录运行、规则、Schema/规则版本、依据断言和推导路径。

工程建议：使用可追溯的证明依赖结构记录直接依据与规则，支持展开解释，不穷举循环形成的无限路径。相同结论由多个有效证明支持时，撤回一个依据不应误删结论。

原始事实、Schema 或规则变化触发受影响推理重算；没有有效支持的当前结论失效，历史保留。推理闭包必须去重并有终止、取消和资源限制，避免传递关系导致不可控膨胀。

推理撤回、重新计算或改用新规则时，保留旧结论的有效状态变更、原规则版本、依据修订和证明关系，支持前后结果对比。重建当前派生图不能改写或丢弃历史证明。

推理结果不能直接执行设备操作；业务规则、权限和审批是独立门禁。高级推理器以后通过适配接口加入，须声明支持的公理和解释能力。

## 12. 身份认证、权限与审计

Keycloak 负责首版 OIDC 身份认证。平台不自研完整密码体系，负责业务角色、用户组、区域授权、本体治理权限和操作审核。

平台内部用户 ID 保持稳定，通过身份绑定关联 OIDC 的 issuer/subject。账号邀请、停用和身份服务管理操作通过适配层处理；未来切换企业身份服务时迁移绑定，保留权限及审计，不凭同邮箱自动合并身份。

工程建议：采用标准授权码登录流程，客户端与后端依所选架构使用 PKCE 等配套保护；具体 Token/会话部署方式在计划中确定。内网使用受控 HTTPS 和本地可用的信任配置。

### 12.1 权限模型

一个用户可具有多个角色、用户组和多个农场/区域范围。每项授权将用户/用户组、角色或允许操作、范围及适用对象绑定在一起，按完整授权项判断，未授权默认拒绝。不得把不同授权项的角色与范围交叉组合：在农场 A 可编辑、在农场 B 只读的用户不能因此编辑 B。Schema 编辑、审核、发布为独立权限；预置角色只是模板，可由前端管理权限配置。

对象主管理归属来自受控管理关系，与服务范围和实际位置分开。管理归属或服务关系本身不向任意用户授予权限；角色的区域范围授权及对象共享授权须明确配置。共享授权可以分别允许查看、使用和特定操作，查看不隐含使用或修改权，“使用”授权也不表示首版启用真实设备控制。

不能让编辑者通过修改归属、关联区域或共享关系给自己扩权。跨范围操作需显式授权；修改授权、角色或区域归属须审计。授权撤销后，后端查询、缓存、导出物访问、长任务和待执行命令均按当前授权重新校验，不能靠旧会话或任务快照继续访问。

工程建议：归属转移与共享授权调整分别形成版本化变更，但联合预览影响，列明原授权哪些保留、撤销或新增，不默认复制旧权限。后续跨区域归属转移按高风险流程处理，审核人须有相应跨区域权限，提交人与审核人不同；执行前重验基线及权限。普通共享调整由具有授权管理权限的人员执行，跨域、扩权或影响重要操作的调整进入风险审批。

候选、证据、导入批次、冲突、重算和导出同样执行范围检查。后台任务具有明确执行身份、授权范围和发起人，不能因为转入 Worker 就绕过权限。

工程建议：首版采用明确范围授权及可解释的继承，暂不开放任意 ABAC 表达式；预留部门、项目和敏感级别等维度。

### 12.2 图查询边界

列表、地图、邻域、路径、SPARQL、聚合、导出必须使用同一权限语义，不得泄露无权对象的名称、位置、关系或计数。

SPARQL 只读入口由后端控制图范围、预算和权限，禁止通过 `SERVICE`、更新语句或任意图访问绕过边界。不能仅在查询结束后隐藏返回节点。

工程建议：派生结论至少存在一条完整、可授权的证明路径才进入该用户查询视图；不能利用受限中间节点推导关系后向无权用户泄露。具体授权视图与缓存实现由工程计划确定，并以越权负例验证。

### 12.3 审计

记录操作者/任务身份、权限范围、目标 IRI、动作、前后摘要、原因、Schema/规则版本、批准记录、结果、时间与关联请求标识。覆盖发布、权限变更、采纳/撤回、合并、同步、重算、回滚及重要拒绝。

审计历史遵守第 10.5 节的不可变记录规则，平台管理员也不能通过应用权限改写或删除历史。来源敏感字段、密码和 Token 不进入可公开图谱或普通日志。

## 13. 地图与离线空间能力

PostGIS 管理业务几何及修订，RDF 保存稳定空间引用和必要语义。切换底图不改变对象 ID、几何、关系、权限或治理逻辑。

工程建议：内部几何以明确 CRS 存储，采用 EPSG:4326 作为通用交换基线；距离与面积使用适当投影/空间计算，来源坐标系、转换和面积来源必须记录。缺失 CRS 或明显异常坐标进入核查，不静默纠正。

### 13.1 底图

前端支持可配置在线服务和本地 MBTiles/PMTiles。工程建议：首版覆盖常用栅格瓦片和 MVT 矢量瓦片的受支持配置，登记边界、缩放级别、样式、图层、来源与许可。

PMTiles 通过支持 HTTP Range 的内网资源服务或等价适配器访问；MBTiles 通过本地瓦片服务读取。地图样式、字体 glyph、sprite、图标和必要脚本全部可本地提供。

提供可分发、来源清楚的演示底图包用于离线验收；农业对象的模拟几何明确标记。底图覆盖外或缺少缩放层级须有提示，不能用一张静态图片冒充可用离线地图。

未来在线影像、遥感与其他地理服务通过图层/资源适配器接入，不占据本体几何的权威位置。

### 13.2 首版空间交互

三个农业场景均支持图层筛选、空间对象选择、详情、关系查看、实例定位和图谱/地图跳转。几何导入、绑定与更新进入受控流程。专业 GIS 制图、完整遥感处理和 3D 不作为首版必交业务。

## 14. 部署、离线交付与运行

本机开发测试；内网服务器通过 Docker Compose 部署。前端、API、Worker、Fuseki/TDB2、内部 PG/PostGIS、Keycloak、文件与地图资源服务分清运行和存储边界。模拟 PG/MySQL 来源作为可选测试组件，与平台库独立。

工程建议：服务器基准为单台 Linux x86-64 容器环境；本机 Windows 使用兼容的 Linux 容器开发环境。实际主机信息及工具链在实施准备阶段只读核查，版本和镜像摘要随后固定。

离线交付包包含版本清单、镜像、初始化与迁移文件、配置模板、Schema/规则产物、合成来源、演示底图与资源、启动/升级/备份/恢复说明和校验摘要。内网部署与运行不要求访问外部包仓库、CDN、API 或云服务。

登录、会话刷新、本地来源接入、RDF 查询、校验、推理、治理和对象管理均可独立运行。外部来源或在线底图失联不会使整个核心平台不可用，来源显示状态与最后成功同步时间。

工程建议：邀请支持内网邮件服务；无邮件条件时通过受控的一次性激活流程交付邀请，开发环境不得伪装邮件已送达。具体发送通道作为部署参数，不能成为核心离线运行的外部依赖。

公网所需的域名、TLS、反向代理与身份配置预留，但首版不部署公网入口或开放数据库管理端口。

### 14.1 命名空间

稳定 IRI 与部署域名、登录服务地址和地图服务地址分开。工程建议：合成开发环境使用明确标记的示例命名空间；接入正式真实数据前，由项目方提供长期可控制的标识命名空间。变更已有正式 IRI 必须经过迁移，而非跟随服务器地址自动重写。

## 15. 备份、恢复与可维护性

备份覆盖内部 PG/PostGIS、Keycloak 数据与配置、OWL/SHACL/规则发布产物、RDF 标准导出、原始快照、附件、离线地图、版本清单及必要密钥恢复资料。

备份须包括完整修订与审计链、历史几何、证据版本、裁决、历史推理结论及证明依赖、稳定身份关联和完整性校验资料，不能只保存最新采纳事实与当前图谱。

工程建议：首版通过受控写入暂停或一致性水位屏障形成可恢复组合，记录各存储快照和投影水位。不得将运行中的任意 TDB2 文件复制视为完整备份。

恢复在隔离环境验证：身份与权限、Schema 版本、实体/关系、候选与裁决、推理依据、任务状态、审计、空间关联和地图资源一致；必要时从权威记录重建 RDF 和派生图。

恢复验收还须抽查代表性历史版本对比、关键变更前后状态与责任人，验证历史链完整性。重建当前图谱不覆盖历史版本；历史查询按恢复后的当前权限执行。

提供健康检查、投影积压/延迟、导入失败、推理与重算任务、权限拒绝及资源监控。不可因某个可选外部数据源不可达而让整个服务健康检查失败。

首版记录恢复耗时和实际恢复点，不将未经演练的 RPO/RTO 数字作为生产 SLA。
